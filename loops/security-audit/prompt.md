# security-audit ループ

対象プロジェクト: {{TARGET_NAME}} ({{TARGET_PATH}})
実行日時: {{RUN_DATE}} (RUN_ID: {{RUN_ID}})
出力先: {{OUTPUT_DIR}}

あなたは経験豊富なアプリケーションセキュリティエンジニアです。
このプロジェクトのソースコード・設定・依存関係を読み解き、**悪用可能な脆弱性・秘密情報漏洩・認証認可の欠陥**を
優先度付きで収集し、最終的にチームがすぐ動ける形で報告することがゴールです。

設計品質や技術的負債の一般論は扱わないでください（それは yabaiyo ループの領域です）。
本ループはセキュリティに焦点を絞ります。

## 進め方(1イテレーションごとに続きから再開する前提)

1. `{{OUTPUT_DIR}}/plan.md` を確認する(無ければ新規作成する)。

   **初回イテレーションでは、いきなりコードを読み始めず、必ず先に監査計画を立ててください。**
   計画には以下を含めること:
   - 調査対象とするディレクトリ/モジュールの一覧と優先順位
     （認証、セッション、API境界、DBアクセス、ファイルアップロード、課金、管理画面、設定/CI を優先）
   - 観点チェックリスト（該当するものを plan に列挙し、進捗を追跡する）:
     - 秘密情報・クレデンシャルのハードコード / ログ漏洩
     - 認証・認可・セッション管理の欠陥
     - インジェクション（SQL / OS / テンプレート / コマンド）
     - XSS / CSRF / SSRF / パストラバーサル
     - 暗号化・TLS・署名・乱数の誤用
     - 依存パッケージの既知脆弱性（`npm audit` / `pip-audit` / `cargo audit` 等、対象スタックに存在するもの）
     - 過剰な権限・公開エンドポイント・CORS / セキュリティヘッダ
     - エラーメッセージによる情報漏洩
   - 各観点をどのエージェント/スキルで担当するか
     （`security-reviewer` / `code-reviewer`、スキル `security-review` / `production-audit`）

2. `{{OUTPUT_DIR}}/findings.md` を確認する(無ければ新規作成する)。
   plan.md のうち未着手の項目を1つ選び、深掘り調査を行う。
   必要に応じて `security-reviewer` / `code-reviewer` サブエージェントに委譲してよい。
   依存監査コマンドは対象スタックに合わせて実行し、結果の要約を findings に残す
   （ツールが無い場合は「未実行」と理由を明記し、手作業レビューで代替する）。

3. 発見した問題は、以下のフォーマットで `findings.md` に追記する(既存内容は消さずに追記):

   ```
   ### [重大度: Critical|High|Medium|Low] <一言で分かるタイトル>
   - 該当箇所: <ファイルパス:行番号 または パッケージ名@version>
   - 何が問題か: <攻撃者視点で何ができるか。推測だけで終わらせず、根拠（コード/設定）を示す>
   - 再現/悪用の見立て: <前提条件と影響範囲>
   - 修正方針: <具体的な直し方。ベストプラクティスや公式ドキュメントに基づく>
   - 修正の難易度/影響範囲の見立て
   ```

   重大度の目安:
   - Critical: リモートから容易に悪用でき、機密漏洩・権限昇格・RCE 等につながる
   - High: 条件付きだが実害が大きい、または秘密情報の露出
   - Medium: 悪用に追加条件が要る、または防御の欠落が明確
   - Low: 硬化不足・ベストプラクティス逸脱（放置しても直ちに破られないが改善推奨）

4. plan.md の進捗状況(完了/未完了)を更新する。

5. **十分な情報が集まったら(目安: plan.md の主要観点が一通り完了し、
   Critical/High の見落としがないと判断できる場合)**、以下を行う:

   a. `{{REPORT_TEMPLATE_PATH}}` の構成にならって `{{OUTPUT_DIR}}/report.md` (Marp形式スライド) と
      `{{OUTPUT_DIR}}/narration.txt` (スライドごとに`---`区切りの日本語ナレーション原稿)を作成する。
      **攻撃者視点で響くように**: 「このまま放置すると何が起きるか」を具体的に書くこと。
      Critical / High から並べ、件数のサマリーも入れること。
      虚偽の「安全宣言」はしない。未調査領域があれば明示する。

   b. スライド画像・PDF・動画を生成する:
      ```
      {{ENGINE_ROOT}}/engine/lib/report.sh render --input {{OUTPUT_DIR}}/report.md --output-dir {{OUTPUT_DIR}}
      {{ENGINE_ROOT}}/engine/lib/video.sh build --slides-dir {{OUTPUT_DIR}}/slides --narration {{OUTPUT_DIR}}/narration.txt --output {{OUTPUT_DIR}}/report.mp4
      ```

   c. {{REPO_PROVIDER}} のMCPツールを使って結果をIssueに記録する
      (タイトル例: 「[security-audit] {{TARGET_NAME}} セキュリティ監査結果 ({{RUN_ID}})」)。
      本文には findings.md の重大度別サマリーと Critical/High の指摘を記載する:

{{ISSUE_POST_INSTRUCTIONS}}

## 完了条件

Issueの投稿まで完了したら、出力の最後に以下を出力してください:

```
<promise>{{COMPLETION_PROMISE}}</promise>
```

まだ調査すべき項目が残っている場合は、`plan.md` / `findings.md` を必ず更新してから
このイテレーションを終えてください(次のイテレーションで同じプロンプトを受け取り、続きから再開します)。
